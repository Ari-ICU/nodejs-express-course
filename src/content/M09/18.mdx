  summary: `As applications evolve, introducing breaking changes (removing fields, altering response shapes, renaming endpoints) without version control breaks existing mobile apps and third-party integrations. **API Versioning** allows legacy and modern clients to coexist seamlessly.

### 1. The Three Versioning Strategies
* **URI Path Versioning (Industry Standard)**:
  * Pattern: \`/api/v1/users\` vs \`/api/v2/users\`
  * Pros: Explicit, easy to test in browsers, simple CDN and reverse-proxy routing rules.
* **Custom Request Header Versioning**:
  * Pattern: \`X-API-Version: 2\` or \`Accept-Version: 2.0.0\`
  * Pros: Keeps URLs clean; allows fine-grained micro-version selection.
* **Content Negotiation / Media Type (Pure REST)**:
  * Pattern: \`Accept: application/vnd.company.v2+json\`
  * Pros: Adheres to Roy Fielding's HATEOAS strict representation model.

### 2. Standard Sunset & Deprecation Signaling
When phasing out older API versions, inform client developers programmatically using standard RFC 8594 HTTP headers:
* \`Deprecation: true\` (or date string)
* \`Sunset: Wed, 11 Nov 2026 00:00:00 GMT\` (Exact date of shutdown)
* \`Link: <https://docs.api.com/migration>; rel="deprecation"\``,
